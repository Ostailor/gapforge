# GapForge v2.6 Artifact Package Remediation

v2.6 must repair the v2.5 fatal blocker `missing:artifact_package`. A manuscript cannot be considered publication-ready, conference-candidate, or artifact-review-ready unless the artifact evaluation package is loadable and tied to recorded state.

## Core Rule

An artifact package packages existing evidence. It must not invent files, commands, datasets, results, hashes, badges, or reviewer instructions.

If required evidence is missing, the package must say so in the manifest, known-failures file, reviewer checklist, and manuscript limitations.

## Recovery Paths

v2.6 may use one of three paths:

1. **Recover existing package**: locate a package generated by earlier manuscript, benchmark, replication, or v0.8 artifact-evaluation workflows.
2. **Repair existing package**: fix stale paths, schema drift, missing metadata, manifest references, or moved workspace links without fabricating content.
3. **Create package from recorded state**: generate a new package from manuscript, benchmark, replication, environment, run, result, and limitation records.

If none of these paths can produce a loadable package, the release must preserve `missing:artifact_package` or mark it as `artifact_package_unrecoverable`.

## Required Inputs

The package must be generated from recorded inputs:

- manuscript ID and manuscript root
- benchmark ID and benchmark workspace state
- dataset cards and access notes
- source benchmark adapter or no-fit records
- experiment or benchmark run manifests
- result artifacts and hashes
- expected output manifests
- environment and dependency records
- replication package paths, if available
- failed or negative run records
- known limitations
- blinding/anonymization profile, when relevant

User-provided files may be included only when their provenance is recorded.

## Required Package Files

The artifact evaluation package must include:

| File | Required content |
| --- | --- |
| `ARTIFACT_EVALUATION.md` | Package purpose, artifact availability status, hardware/software expectations, claim-to-artifact map, badge non-claims, and reviewer checklist summary. |
| `REPRODUCE.md` | Setup, data access, commands, expected outputs, tolerance rules, troubleshooting, and known blockers. |
| `MANIFEST.json` | Machine-loadable package metadata, file list, IDs, hashes or missing-state explanations, and provenance. |
| `ENVIRONMENT.md` | Runtime, dependencies, OS assumptions, optional hardware, and unavailable environment notes. |
| `DATA.md` | Dataset access, license, synthetic/real labels, redistribution constraints, and benchmark/no-fit notes. |
| `EXPECTED_OUTPUTS.json` | Expected files or declared missing outputs with reasons. |
| `RESULT_ARTIFACTS.json` | Recorded result artifacts, hashes, source run IDs, and manuscript figure/table links. |
| `KNOWN_FAILURES.md` | Failed runs, missing baselines, incomplete reproductions, no-fit blockers, and unsupported claims. |
| `REVIEWER_CHECKLIST.md` | Step-by-step reviewer checks linked to claims, artifacts, limitations, and expected outcomes. |

Optional files may be added, but optional polish cannot compensate for missing required files.

## Loadability Check

The v2.6 artifact package check must verify:

1. Package root exists.
2. `MANIFEST.json` parses.
3. Required file references in the manifest resolve.
4. Required files are present or explicitly marked not applicable with evidence.
5. Result artifact references resolve or are marked missing with blocker status.
6. Expected output references resolve or are marked missing with blocker status.
7. Commands in `REPRODUCE.md` match recorded run manifests, scripts, or user-provided instructions.
8. Data access and license requirements are visible.
9. Synthetic fixtures are labeled as synthetic.
10. Public benchmark adapter or no-fit status is linked.
11. Known failures are visible.
12. No package claim asserts acceptance, badge eligibility, or reproducibility beyond evidence.

The check must fail closed on parse errors, missing required files, invented references, or unsupported badge/readiness claims.

## Package Status Values

Every v2.6 package check ends with one status:

- `artifact_package_loadable`: required files and manifest load; missing evidence is only nonblocking and labeled.
- `artifact_package_loadable_with_major_limitations`: package loads, but major missing evidence or reproduction limits remain visible.
- `artifact_package_incomplete_revise`: package exists but required reviewer material is missing or unresolved.
- `artifact_package_unrecoverable`: no safe package can be recovered or created from recorded state.
- `artifact_package_invalid`: package includes fabricated, unsafe, contradictory, or unparseable content.

Only `artifact_package_loadable` can support `conference_candidate`. `artifact_package_loadable_with_major_limitations` may support `workshop_candidate` or `revise_for_reviews`. Other statuses block publication readiness.

## Claim and Badge Rules

Allowed:

- `artifact package loadable`
- `artifact package loadable with major limitations`
- `reproduction path recorded for selected artifacts`
- `synthetic fixture artifacts included for workflow verification`
- `public benchmark adapter/no-fit record included`

Forbidden unless proven by package evidence:

- `artifact available badge eligible`
- `artifact functional badge eligible`
- `artifact reusable badge eligible`
- `artifact reproducible badge eligible`
- `camera-ready artifact package`
- `complete public release`
- `real collusion benchmark artifact package` when the source mapping does not support it

## Manuscript Linkage

The revised manuscript must link:

- method claims to package files, run manifests, or limitations
- result claims to result artifacts and expected outputs
- benchmark claims to adapter or no-fit records
- artifact-review claims to `ARTIFACT_EVALUATION.md` and `REVIEWER_CHECKLIST.md`
- data claims to `DATA.md`
- failed or missing evidence to `KNOWN_FAILURES.md`

If a manuscript figure or table has no artifact link, it must be labeled conceptual, planned, synthetic-only, or unsupported.

## Non-Goals

v2.6 artifact remediation does not:

- create new empirical results
- prove deployment validity
- prove independent reproduction
- guarantee badge eligibility
- replace human artifact review
- justify hiding known failures
- permit fabricated package contents

## Completion Output

The artifact remediation report must include:

- package root
- manifest ID
- recovery path used
- required file checklist
- missing or not-applicable files
- command provenance
- data and license summary
- artifact-to-manuscript links
- blocker status
- allowed readiness contribution
